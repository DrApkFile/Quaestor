A. QCAI stage 1 result for Books v2

Dashboard: Framework EVM/Solidity. Score 65/100, risk HIGH, quantum safe "Not scored", 5 findings. The dashboard offered no public report link; the exported PDF is the record. Claude triaged all five as false positives or informational.

Record each in docs/AUDIT.md in plain language: what the auditor claimed, what the code actually does, our verdict, and a test that proves it. Add any missing tests to contracts/test/Books.t.sol.

Q1 HIGH, "missing access control on anchorEntry/anchorGrant".
Claim: they only check ownership, so unauthorised users could change entries or grants.
Reality: ownership is the authorisation rule. requireOwner reverts NotOwner unless msg.sender == books[book], the address that registered the book.
Verdict: false positive.
Test: a non-owner calling anchorEntry, anchorGrant and closePeriod each reverts NotOwner, and state is unchanged.
Q2 MEDIUM, "overflow in index + 1".
Claim: nextIndex could overflow at uint64.max.
Reality: Solidity 0.8.24 checks arithmetic and reverts (panic 0x11), so it never wraps. Reaching it would need 2^64 entries in one period.
Verdict: false positive.
Test: vm.store nextIndex to type(uint64).max; the next anchor reverts with panic 0x11 and state is unchanged.
Q3 MEDIUM, "unchecked return values from pqcKeyStatus/pqcVerify".
Claim: if these calls fail, execution continues with bad assumptions.
Reality: both are checked. pqcVerify == false reverts BadSignature. pqcKeyStatus must be registered, have a 2592-byte key, use algorithm 1 (ML-DSA-87) and show possession proven, or it reverts with a specific error. A missing precompile returns no data, and the ABI decode reverts, so it fails closed.
Verdict: false positive.
Tests: each pqcKeyStatus failure gives its specific error; a bad signature gives BadSignature and the period stays open; with no code at 0x0A02 the call reverts.
Q4 LOW, "front-running book registration".
Claim: an attacker who sees your salt can register your book first.
Reality: the ID is keccak256(msg.sender, salt). An attacker using your salt gets a different ID under their own address.
Verdict: false positive.
Test: a second sender using the same salt gets a different ID, and the original owner then registers successfully.
Q5 INFO, "unbounded nested mappings may exhaust gas".
Claim: growing mappings make reads and writes more expensive.
Reality: a mapping read or write costs the same at any size, and the contract never loops over a mapping.
Verdict: informational, no risk.
Test: none needed; state the reasoning.
