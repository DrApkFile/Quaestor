# PRD: Quaestor

Version 1, 2026-11-20. Single source of truth. Changes → DECISIONS.md entry, then edit here.

## 1. Goals and non-goals
**Goal:** a normal web app where a business pays and gets paid **privately** on QoreChain testnet (our deployment of Gloam's open-source shielded pool), every payment writes a book entry **sealed in the browser** with ML-KEM-1024 + X25519 and signed ML-DSA-87, and the business can grant an auditor **one period** of the books, which the auditor can open and check against the chain.

**Non-goals:** PWA or native app; mainnet; a post-quantum pool (Groth16 stays classical); multi-user businesses with roles; tax calculations; fiat on/off ramps; any Gloam hosted service (relay, API keys, hosted MCP, gloam.trade artifacts); AI features in the product.

## 2. Hook, loop, boundary
Hook: "Private to the world. Open to your auditor. One quarter at a time." Loop and boundary: IDEA_CHECK.md.

## 3. Architecture
```
contracts/
  gloam/           Gloam MIT contracts, vendored at a pinned commit, unmodified (credited)
  script/          our deploy script for PoseidonT3, final verifiers, ShieldPoolPayments, GloamPayMemo on Diana
  Books.sol        anchors, grants, period close (ours)
packages/core      pure TS, no network, no clock: entry/grant/close codecs, period keys, ticket codec, verdict engine, reconciliation
packages/chain     Diana reads pinned to one height, KEM/ML-DSA registry, EVM windows, pool wrapper over @gloamtrade/sdk (chainId 9800 + our poolAddress), tree sync from the pool’s insertion events (Shielded, Transferred)
apps/web           Vite + React on Vercel; M5 Account, Public check, Auditor; Business/Pay remain M6
BlobBoard.sol      permissionless event-only on-chain ciphertext board, indexed by SHA3-256; no data server (D14)
apps/audit-cli     `quaestor-audit <book> --period <p> --key <file>` read-only verdicts from a terminal
public/circuits    self-hosted Gloam final wasm/zkey/vkey (shield, transfer, unshield, receipt, payroll_total, funds)
evidence/          generated by scripts, never hand-written
```

## 4. Accounts and keys (decision D1)
Every user (business, client, supplier, auditor) gets an **in-app QoreChain account** created in the browser (mnemonic → secp256k1 + ML-DSA-87 via QoreSign; seal keys via `deriveSealKeys`). Mandatory encrypted backup file before first use. Onboarding: register ML-DSA-87 key (with proof of possession) → register ML-KEM-1024 key (`MsgRegisterKEMKey`) → sign and publish a recipient card → open an EVM window when paying. QoreX optional for funding the account.

## 5. Vocabulary
- **Book:** one business's ledger, id = `keccak256(businessEvmAddress, salt)`.
- **Period:** a labelled time span with its own random 32-byte key. Default length = calendar quarter. Demo book uses **1-day periods, labelled "demo-scale periods"** so we can show a granted and a refused period before 2 Dec.
- **Entry:** one payment in or out, sealed under the period key, signed ML-DSA-87 by the business, anchored on chain.
- **Grant:** the period key sealed to the auditor's registered key + a signed grant record anchored on chain.
- **Entry verdicts (closed):** `MATCHED`, `UNBACKED`, `TAMPERED`, `UNKNOWN`.
- **Period verdicts (closed):** `HOLDINGS_COVER_BOOKS`, `HOLDINGS_SHORT`, `UNKNOWN` (D5 holdings coverage, not complete reconciliation).
- **UI error codes (closed):** `WINDOW_CLOSED`, `NO_PQ_KEY`, `PQ_POSSESSION_NOT_PROVEN`, `NO_KEM_KEY`, `CARD_INVALID`, `NOT_GRANTED`, `WRONG_CONTEXT`, `NOTE_SPENT`, `OUTCOME_UNKNOWN`, `NETWORK_UNAVAILABLE`.

## 6. Flows and wire formats
**Pay (private send)**
1. Payer's browser resolves the payee's qor1 address → ML-KEM key from registry + verified recipient card. No key → `NO_KEM_KEY`, no payment.
2. `buildPrivateSendIntent({ chainId: 9800, poolAddress, ... })` → proof in the browser → `transfer` on Diana through the payer's window.
3. **Ticket** = Gloam note package for the payee's output note, sealed with QoreSeal hybrid and anonymous envelopes, purpose `quaestor:ticket`, AAD = `9800|pool|paymentCommitment`, recipients = payee (+ payer's own key for its records). Posted via our `GloamPayMemo.postMemo(paymentCommitment, ticket)`. No P-256 path exists.
4. Payee's app scans memos, attempts anonymous opening, skips non-recipient decryption failures, opens the ticket, verifies the commitment is in the tree, stores the note.

**Book entry** (both sides keep books if they use Quaestor; demo: the business)
```json
{ "v": 1, "book": "0x…", "period": "2026-11-27", "index": 4, "prevEntrySha3": "…",
  "direction": "OUT", "asset": "0x…fUSD", "amount": "250000000",
  "paymentCommitment": "0x…", "counterparty": { "address": "qor1…", "name": "Hosting Co (demo)" },
  "purpose": "November hosting", "category": "infrastructure", "invoice": { "sha3": "…", "bytes": 48211 },
  "receipt": { "proof": "…", "publicSignals": ["root","commitment","asset","minAmount","reveal","shownAmount","context"] } }
```
- `receipt.context = proofContext("quaestor|<book>|<period>|<index>")`. Proof made with Gloam's receipt circuit (exact amount).
- Entry JSON canonicalised → sealed under the period key (`PrivateBatchCodec`, context `quaestor:<book>`) → signed ML-DSA-87 over the blob's SHA3-256 (QoreSign `signMessage`) → blob + signature to BlobBoard → `Books.anchorEntry(book, periodId, index, blobSha3, prevSha3)`.
- Invoice file sealed the same way, its hash inside the entry.

**Grant**
`sealEpochKey`-style envelope of the period key to the auditor (purpose `quaestor:<book>:period-key`, AAD = `book|period|auditorAddress`), grant record `{book, period, auditor, envelopeSha3, issuedAt}` signed ML-DSA-87 → BlobBoard → `Books.anchorGrant(...)`. Grants can't be revoked for that period (stated in the UI).

**Close period**
Close record `{book, period, entryCount, lastEntrySha3, priorSha3, closingBalance, cashOutFees, holdings proofs}` signed ML-DSA-87 → `Books.closePeriod(...)`, which checks the signature with **pqcVerify** against the business's key from **pqcKeyStatus** (`possessionProven` required). If S09 shows the precompiles inactive, the contract stores the signature and the verdict engine checks it (D3).

## 7. Books.sol
- `registerBook(bytes32 salt, bytes32 openingSha3)` → book id, owner = msg.sender (must pass `_requireProvenPqKey`).
- `anchorEntry(bytes32 book, bytes32 period, uint64 index, bytes32 blobSha3, bytes32 prevSha3)` — owner only; `index == nextIndex`; `prevSha3 == lastSha3`; period not closed.
- `anchorGrant(bytes32 book, bytes32 period, address auditor, bytes32 grantSha3)` — owner only.
- `closePeriod(bytes32 book, bytes32 period, uint64 entryCount, bytes32 lastEntrySha3, bytes32 closeSha3, bytes calldata mlDsaSignature)` — owner only; verifies as above; locks the period.
- Events for each; custom errors; no strings; Foundry tests.

## 8. Verdict engine (packages/core/verdict.ts), per entry, first failure returns
1. Blob, signature or anchor unavailable → `UNKNOWN(reason)`.
2. SHA3-256(blob) ≠ anchored `blobSha3`, or `prevSha3` chain broken → `TAMPERED`.
3. ML-DSA-87 signature invalid for the book owner's on-chain key → `TAMPERED`.
4. Open with the granted period key; failure → `UNKNOWN(NOT_GRANTED)` (the auditor UI shows `NOT_GRANTED`).
5. Among entries openable by this auditor, later occurrences of a paymentCommitment in the same book are `UNBACKED(DUPLICATE_PAYMENT)`; preserve audit scope across granted periods in their ordered traversal. No on-chain payment uniqueness index is used.
6. Receipt: `context` ≠ expected for (book, period, index) → `UNBACKED`.
6. Receipt Groth16 verification (receipt vkey) fails → `UNBACKED`.
7. `commitment` ≠ entry's `paymentCommitment`, `shownAmount` ≠ amount, or asset mismatch → `UNBACKED`.
8. `root` is not a root the pool tree ever had (rebuilt from the pool’s insertion events (Shielded, Transferred); not `isKnownRoot`, which keeps only 100) → `UNBACKED`.
9. Else `MATCHED`.
`MATCHED` does not establish who the counterparty is in real life, or that every payment was booked.

## 9. Reconciliation (D5, decide by day 4)
D5 (Claude/builder, M4): signed opening balances per asset are anchored at registration. Closing balances are previous closing balance (or opening) + Σ IN - Σ OUT - Σ cash-out fees. A context-bound Gloam funds proof (at most four distinct notes) establishes holdings at least the declared closing balance. Validate the proof against self-hosted funds_vkey.json, the root against full insertion history, and every nonzero revealed nullifier against spent at the actual close block, pinned. Consolidate to self if more than four notes are needed.

Period results are HOLDINGS_COVER_BOOKS, HOLDINGS_SHORT or UNKNOWN. Never show adds up. A lower-threshold valid proof is insufficient coverage; missing/invalid proof or spent backing is UNKNOWN. This does not detect collusive hidden income or payments from unbooked funds. See DECISIONS D5 and THREAT_MODEL.md.

## 10. State machines
- Payment: `PLANNED → PROVED → BROADCAST → LANDED → TICKET_POSTED → BOOKED → ANCHORED`, with `OUTCOME_UNKNOWN` held (never re-sent while the nullifier may be used).
- Note (browser): `INCOMING → OWNED → SPENDING → SPENT` (SPENT only after a receipt).
- Period: `OPEN → CLOSING → CLOSED`; `CLOSING` refuses while any entry is `UNANCHORED`.
